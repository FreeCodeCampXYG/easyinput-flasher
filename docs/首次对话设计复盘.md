# 复刻 EasyInput Flasher：从最小闭环到设计复盘

> 记录日期：2026-08-31
> 项目：EasyInput Flasher
> 目的：让读者先能按步骤复刻一个安全的硬件烧录器，再理解首次方案如何被拆解、实现、修正与扩展。
> 结论边界：本文记录的是“软件设计与实现已达到可构建、可审计、可继续实机验证”的状态，不宣称所有硬件功能已经实测通过。

## 0. 先读这一章：如何复刻一个安全烧录器

如果你只想复刻项目，先完成本章；后续章节解释每个设计为什么存在。目标不是复制一套 UI，而是复刻一条可信的固件交付链路。

### 0.1 先判断你的目标是否匹配

这个项目适合以下场景：你的硬件使用固定芯片和固定 Flash 布局；你希望开发者在 GitHub Actions 构建固件，普通用户只下载 Release 并安全写入；你愿意把“构建成功、写入成功、设备恢复、功能可用”分开验证。

它不适合把任意 `.bin`、任意下载 URL、任意串口命令直接做成一键写入工具。若你的目标是无边界烧录，本文的安全合同会刻意阻止你这样做。

### 0.2 复刻后的最小成品

完成第一版后，用户应该能够完成这条流程：

```text
开发者打 tag
  -> GitHub Actions 构建并发布 Release
  -> 用户在桌面端选择受信 Release
  -> 应用校验 manifest 与镜像 SHA-256
  -> 用户让设备进入下载模式
  -> 应用只读核验芯片与设备尾号
  -> 用户确认后写入固定三段镜像
  -> 设备恢复正常启动，应用检查 HID
```

成功标准不是“按钮可点”，而是：错误芯片、错误板型、缺清单、哈希不一致、来源未受信、设备变化等情况都不能写入。

### 0.3 需要准备的四件事

| 准备项 | 你需要明确的内容 | EasyInput 示例 |
| --- | --- | --- |
| 硬件合同 | 芯片、下载模式操作、正常模式识别方式、恢复动作 | ESP32-S3；开机短按 BOOT；正常模式为 HID/BLE；烧录后关机再开机 |
| 固件合同 | 固定镜像名称、偏移、版本标识和校验方式 | bootloader `0x0`、分区表 `0x8000`、应用 `0x10000` |
| 发布合同 | 谁构建、在哪构建、哪些文件才能发布 | GitHub Actions 构建；Release 必须有 manifest、三段镜像和 SHA-256 |
| 桌面端合同 | 哪些参数可由前端请求，哪些只能由后端决定 | 前端只选择和确认；Go 后端从校验后的 manifest 生成写入计划 |

硬件合同必须在写代码前从原理图、芯片文档和已有实机记录中确认。不要从网上的通用烧录示例推断你的 BOOT 操作或 Flash 偏移。

### 0.4 用这个目录开始，而不是从一个大页面开始

```text
your-flasher/
  frontend/                 Wails 前端：只显示状态和收集确认
  internal/application/     状态机、Wails 绑定、二次权限检查
  internal/firmware/        Release、manifest、SHA-256、缓存
  internal/device/          正常模式识别、下载端口、恢复检查
  internal/flasher/         芯片协议与固定镜像写入
  internal/config/          代理和用户本地设置
  docs/                     架构、发布规范、故障排查、用户手册
  .github/workflows/        CI 与 tag 驱动 Release
```

复刻时，先把 Go 后端的 `firmware`、`device` 和 `flasher` 写成可测试模块；前端最后接入。因为 UI 不能成为写入范围或来源信任的唯一防线。

### 0.5 七步复刻路线

#### 第 1 步：固定硬件操作

写一张硬件操作卡，至少回答：设备怎样进入下载模式？正常启动后如何识别？烧录后如何恢复？错误操作会发生什么？

EasyInput 的答案是“正常开机后短按并松开 BOOT，烧录完成后关机再正常开机”。这不是 UI 文案，而是状态机门禁。没有这张卡，不要开始做“一键烧录”。

#### 第 2 步：让 CI 产出可验证的 Release

不要让桌面端编译固件。让固件仓库在 tag 触发的 GitHub Actions 中完成测试和构建，再发布：

```text
firmware-manifest.json
bootloader.bin
partition-table.bin
application.bin
SHA256SUMS.txt
构建溯源或构建说明
```

manifest 至少包含 `board`、`chip`、`tag`、`commit`、构建工具版本、每个文件的名称、大小、偏移和 SHA-256。桌面端只接受满足该合同的 Release。

#### 第 3 步：实现下载和校验，暂时不连设备

先让桌面端读取指定 GitHub 仓库的 Release。下载后做四项检查：来源是否受信、板型是否正确、芯片是否正确、每个文件的大小和 SHA-256 是否匹配。任一项失败都只保留诊断，不进入写入阶段。

这一步可完全用单元测试完成，也是复刻时最容易获得稳定反馈的阶段。

#### 第 4 步：实现只读设备验身

把“设备正常在线”和“设备处于下载模式、可写入”建成两个不同状态。先扫描正常 HID/BLE 作为操作提示；用户按硬件合同进入下载模式后，才扫描串口并只读读取芯片型号和脱敏设备标识。

端口重新枚举后必须重新验身；识别到的设备尾号变化时停止，不沿用上一次选择。

#### 第 5 步：让后端锁定写入计划

只有以下条件都满足时，后端才创建写入会话：

1. 选择的 Release 来自本轮已加载的受信来源。
2. manifest 的板型、芯片、文件角色和偏移通过固定规则。
3. 下载资产逐项校验通过。
4. 本轮下载模式设备已验身；真正启动写入前再次只读读取设备标识，且 MAC 尾号必须与本轮验身和确认文本绑定的对象一致。
5. 用户输入本轮生成的确认文本。

若写前复核的设备标识不一致，保留脱敏诊断并终止本次写入。写入时锁定来源、版本和端口；前端不能修改命令、路径、偏移或“trusted”标记。

#### 第 6 步：把恢复和功能验证拆开

写入完成后，提示用户按硬件合同恢复正常启动，再检查预期 HID/BLE 是否出现。UI 至少输出三种不同结果：

| 结果 | 代表什么 |
| --- | --- |
| 写入完成 | 固定镜像已由烧录协议处理完成 |
| 设备恢复 | 正常模式 HID/BLE 已重新出现 |
| 功能待验证/已验证 | 按键、音频、BLE、业务功能需要单独实测 |

#### 第 7 步：最后才开放社区来源

第一版只接官方仓库。社区来源先只读审计，检查 Release、manifest、三段镜像和自动发布流程；再通过精确 Release 审批开放写入。不要把“GitHub 搜到的仓库”直接提升为可信固件。

### 0.6 开发和验收顺序

| 阶段 | 可在没有实板时完成 | 必须用真实设备完成 |
| --- | --- | --- |
| manifest/哈希/来源门禁 | 单元测试、反例测试 | 不需要 |
| Release 下载与缓存 | API mock、集成测试 | 可选网络检查 |
| 下载模式验身 | 协议封装和错误分支测试 | 芯片、端口、重枚举 |
| 固定三段写入 | 参数和状态机测试 | 写入、取消、拔线、错误芯片 |
| 恢复与功能 | UI 状态测试 | 断电重启、HID/BLE、具体业务功能 |

完成每一行再进入下一行。CI 绿灯仅说明构建和测试通过，不能替代任何需要实机完成的验收项。

### 0.7 复刻前的最后检查

- [ ] 我已确认板型、芯片、BOOT 操作、恢复操作和固定偏移。
- [ ] CI 会生成带 commit、哈希和三段镜像的 manifest。
- [ ] 后端而不是前端决定命令、路径、偏移和来源信任。
- [ ] 正常模式检测与下载模式验身是两个状态。
- [ ] 写入、恢复和业务功能会分别报告。
- [ ] 社区来源不能在未审计时写入设备。

做到这些，读者已经能复刻项目的核心；后面的内容用于理解为什么项目最终采用了这套做法。

## 1. 一句话概括

EasyInput Flasher 的核心不是把烧录“做成一个按钮”，而是把原先依赖个人电脑、个人环境和人工记忆的固件交付流程，收敛为一条可验证的链路：**GitHub Actions 构建固定版本固件，GitHub Release 分发带清单和哈希的三段镜像，桌面端在验明设备、核验来源并取得人工确认后才写入。**

这使普通使用者不必安装 ESP-IDF，也使固件开发者可以把注意力放回功能本身；但它没有、也不应该取消硬件操作和安全确认。

## 3. 设计起点：用户真正要解决的问题

最初的问题并非“怎样调用一次烧录命令”，而是四个相互关联的痛点：

1. 固件构建依赖个人电脑上的环境，其他人无法稳定复用。
2. 烧录步骤依赖对 BOOT、端口变化和镜像偏移的记忆，容易误操作。
3. 想体验其他人的功能，但不能让任意 GitHub 链接直接获得写入设备的权限。
4. 希望把构建、版本、下载、日志、发现和帮助变成一个可维护的桌面工具。

因此，最先设计的不是界面，而是两个合同：

```text
固件仓库合同：源码 -> CI 构建 -> manifest + 三段镜像 + SHA256 -> Release
桌面端合同：受信 Release -> 下载校验 -> 下载模式验身 -> 人工确认 -> 固定范围写入 -> 恢复检查
```

只有这两个合同都成立，才存在安全意义上的“一键烧录”。

### 4.3 运行中发现的硬件认知修正

初版很快遇到一个容易被忽略的事实：**正常模式的 EasyInput 并不保证有 CDC 串口。** 在正常启动时，它可以作为 HID/BLE 设备出现；下载模式才会出现可供 ESP32-S3 ROM 通信的 COM 端口。

| 初始假设 | 证据 | 最终设计 |
| --- | --- | --- |
| “扫描不到串口”可能意味着设备未连接 | Windows PnP 实际枚举到 `EasyInput AI` Bluetooth LE；正常 HID 也不一定有串口 | 正常 HID/BLE 只表示设备在线，界面提示用户短按并松开 BOOT 后再刷新下载端口 |
| 芯片信息可在普通扫描阶段显示 | 正常 HID 不足以证明芯片型号 | 只有下载模式下执行只读验身，才显示 ESP32-S3 与脱敏 MAC 尾号 |
| `chip-id` 是通用验身命令 | ESP32-S3 上该调用会返回非零，界面误报工具失败 | 改为 ROM 兼容的 `read-mac` 与 `flash-id`；后续切到进程内纯 Go 协议仍保留同样边界 |

这正是烧录器需要状态机而不是“扫描到设备就写”的原因。

### 4.4 main 还原与社区固件如何不失控

后续对话把需求聚焦为两个实际场景：恢复官方 `main` 和体验社区/Fork 固件。

| AI 的可公开答复 | 用户的原始提示 |
| --- | --- |
| 只读审计确认：当时 `origin/main` 缺少可被烧录器消费的固件 Release workflow 和 manifest 脚本，不能把分支名直接当“还原包”。正确做法是由 Maker 主分支 CI 创建绑定 commit 的官方 `firmware-v-main-*` Release。 | “目前烧录功能是可以用了，但是还差点东西，比如还原 main 分支的功能……如果想要体验别人的功能进行烧录……主要不想在里面套上编译……需要建议他们搞一个自动化编译流程，然后编译规范。” |
| 社区接入必须先修复后端来源绕过、任意文件名、任意偏移和分区布局未约束的问题；贡献者复用统一 Actions 模板，在 Fork 中改功能、跑测试、打 tag，烧录器继续只消费预编译 Release。 | 同上 |

实现后，后端要求选择项必须来自本轮加载的受信来源，manifest 只能描述下列三段：

| 文件角色 | 固定偏移 | 作用 |
| --- | ---: | --- |
| bootloader | `0x0` | 启动程序 |
| partition-table | `0x8000` | 分区布局 |
| application | `0x10000` | EasyInput 应用固件 |

前端的“已校验”文案也改为“来源受信”，避免用户误以为尚未下载的固件已完成哈希校验。

## 5. 最终的软件与硬件设计

### 5.1 架构分层

```text
Wails 前端
  -> internal/application  状态机、Wails 绑定、二次门禁
  -> internal/firmware     GitHub Release、manifest、SHA-256、缓存
  -> internal/device       正常 HID/BLE 识别、下载端口、恢复检查
  -> internal/flasher      ESP32-S3 ROM/stub 通信与固定三段写入
  -> internal/config       代理、收藏来源、用户本地设置
```

这里最重要的权限边界是：**前端是请求者，不是烧录指挥者。** 前端不能传入任意 shell 命令、偏移、本地路径或“已经信任”的布尔值来绕过 Go 后端。

### 5.2 设备状态机

```text
正常模式设备在线
  -> 用户短按并松开 BOOT
  -> 刷新下载端口
  -> 只读验身：ESP32-S3 + MAC 尾号
  -> 选择受信 Release
  -> 下载并逐文件 SHA-256 校验
  -> 输入本次设备的确认文本
  -> 锁定端口/来源/版本，写入固定三段镜像
  -> 用户关机，再正常开机
  -> 检查 HID 恢复
  -> 标记“功能验证待进行”
```

其中的阻断条件包括：芯片不是 ESP32-S3、板型不是 `easyinput-v2`、manifest 文件角色或偏移不正确、哈希不匹配、端口变化后 MAC 不一致、来源未受信、确认文本不匹配。任一条件失败，保持缓存和诊断信息，但不写入设备。

### 5.3 证据不能混写

| 证据 | 能说明什么 | 不能说明什么 |
| --- | --- | --- |
| GitHub Actions 成功 | runner 能构建、测试和归档 | 真机可连接、可写入、功能可用 |
| manifest/哈希通过 | 下载资产与声明一致 | 固件业务功能正确 |
| 写入工具成功 | 固定三段数据按本次流程写入 | 设备已退出下载模式、功能已恢复 |
| HID 恢复 | 预期设备枚举回来了 | 按键、BLE、音频、Host Action 等功能正确 |
| 实板功能清单回归 | 指定的真实功能已验证 | 未测平台或未测功能也通过 |

把这些证据拆开，是本项目对“软件设计到可以”的定义：每个结论都有对应证据，不让构建绿灯替代硬件事实。

## 6. 实现过程中的坑与可复制经验

### 6.1 固件供应链先于 UI

最初的 Release 可提供镜像，但没有足够的机器可读元数据。若桌面端从文件名或 GitHub 搜索结果猜写入范围，社区固件会变成供应链漏洞。

可复制的做法：由构建端生成 manifest；manifest 同时记录 `board`、`chip`、tag、commit、IDF 版本、文件名、大小、偏移和 SHA-256；烧录端只从校验后的 manifest 构造写入计划。

### 6.2 “一键”不能替代用户完成 BOOT

EasyInput V2.0 的操作合同是：设备正常开机后，短按并松开 BOOT；完成烧录后，关机再正常开机。把它伪装成自动重置或“按住 BOOT 上电”，会把硬件状态变得不可预测。

可复制的做法：UI 把操作拆成可理解的阶段，正常模式只做在线确认，下载模式才开放验身和写入；不要默认整片擦除。

### 6.3 用真实芯片族命令验证，不套通用示例

ESP32-S3 对 `chip-id` 的失败说明，工具示例不能替代真实设备的只读验证。后来采用 ROM 兼容路径，并在用户授权后切换到 `tinygo.org/x/espflasher v0.8.1` 的进程内纯 Go 实现，减少了 Python/PyInstaller/helper 打包和 GPL 副本的维护面。

可复制的做法：先以只读命令确认芯片、端口和退出码语义，再改状态机；替换烧录引擎时，先保持 manifest、MAC 确认、取消和恢复门禁不变，再做实板回归。

### 6.4 正常设备检测与下载模式验身是两件事

把 BLE/HID 当作“芯片已验证”会误导用户；把没有串口当作“设备未检测到”也会误导用户。

可复制的做法：前端文案和后端类型显式区分 `normal device present` 与 `download-mode verified`，不要复用一个笼统的“已连接”状态。

### 6.5 发布矩阵的成功不能掩盖产物错误

六平台原生 runner 能避免交叉编译假象，但仍出现过 WebKitGTK 版本、Python helper 架构、publish job 未 checkout、同名归档覆盖等问题。

可复制的做法：每个平台的包名包含架构；发布后下载公开资产重新计算 SHA-256 并检查压缩包内容；package jobs 成功但 publish 失败时复用 artifacts，而不是无谓重跑全矩阵。

### 6.6 社区生态必须先有审计和治理

“发现”功能的危险在于它看似只是搜索，实际上可能引导用户写入固件。社区仓库的接入不能因为有 Release 就默认可信。

可复制的做法：先只读审计公开 Release、manifest、三段镜像、自动发布 workflow 和 manifest 脚本；用户输入精确确认文本后，来源才进入本地受信列表。再配合 Issue/PR 模板、CODEOWNERS、CodeQL、人工批准和原生 auto-merge 门禁，AI 审核只能给建议，不能批准或合并。

## 7. 给后来者的实施清单

### 阶段 A：先定义合同

1. 明确目标板、芯片、下载模式和恢复操作，不从通用 ESP 示例推导。
2. 确定不做的事：本地编译、任意 URL、裸 bin、默认擦除、未经确认的自动重置。
3. 编写 manifest schema 和固定镜像布局；为正例和反例写单元测试。
4. 规定“构建、下载校验、写入、恢复、功能”五类证据的报告格式。

### 阶段 B：构建端自动化

1. 用 tag 固定源码 commit。
2. 在 CI 中运行宿主测试和目标固件构建。
3. 生成 manifest、三段镜像、`SHA256SUMS.txt` 和构建溯源。
4. 只把完整、可验证的资产发布为 Release。

### 阶段 C：桌面端最小闭环

1. 只读取指定官方 Release。
2. 下载后逐文件验 manifest、大小与 SHA-256。
3. 扫描下载端口并只读验明芯片和 MAC 尾号。
4. 让用户明确确认本次设备和版本，再写固定三段。
5. 写入后要求完整断电重启，再检查正常 HID。
6. 给失败状态提供下一步，而不是只显示原始工具错误。

### 阶段 D：在闭环稳定后扩展

1. 收藏官方/社区来源，保留来源的信任级别。
2. 加入只读发现和精确 Release URL 审批。
3. 提供 Fork 到 Release 的贡献者教程，而非让贡献者手工填偏移。
4. 扩展多平台打包、签名、公证和真实平台硬件回归；每项独立取证。

## 8. 当前进度与后续规划

### 8.1 已经形成的能力

- 独立 Wails v2 + Go 桌面项目，未污染 Maker 固件仓库。
- 受信 GitHub Release 加载、manifest、三段镜像 SHA-256、缓存、设备验身、MAC 尾号确认、取消和恢复检查状态机。
- 正常 HID/BLE 和下载模式串口的分层识别；BOOT 操作和关机重启提示。
- 纯 Go ESP32-S3 烧录适配、六平台 CI/Release 打包、SHA-256 和构建溯源。
- 固件库、发现、日志、更新、关于/帮助页面，以及用户手册、架构、构建、发布、故障排查和社区教程。
- 官方 main 与社区固件的同一 Release 合同，后端固定来源、文件角色和偏移门禁。

### 8.2 必须继续完成的验证

1. 当前仅完成官方 main Release 与 manifest 的核对；必须在新版桌面包和真实设备中跑通“Release 显示、下载哈希、短按 BOOT、验身、写入、关机重启、HID 恢复”的全链路。
2. 验证错误芯片、哈希篡改、取消、拔线、多设备和端口变化等失败路径。
3. 对 Windows x64 以外的平台先明确物理设备、操作者和验收项，再分别验证串口权限、应用签名/系统安全提示与真实烧录；不得用 CI 成功或计划替代这些证据。
4. 解决或在 CI 中复核 Windows 本机 `application` 测试的 `Access is denied` 执行限制。

### 8.3 将其他人的内容纳入进来的路线

这部分应该按风险逐层开放，而非一次做成“任何人都能上传并烧录”。

| 阶段 | 能力 | 写入权限 | 进入条件 |
| --- | --- | --- | --- |
| 1 | 读取官方 main 基线 | 官方来源可写 | CI、manifest、哈希、实机回归齐全 |
| 2 | 社区仓库只读审计 | 不可写 | 有公开 Release 与完整资产 |
| 3 | 精确 Release 审批 | 指定版本可写 | 维护者审核来源、commit、板型和变更说明 |
| 4 | 贡献者自助发布 | 审核后可写 | Fork Actions 模板、测试、manifest、Release 合同全部符合 |
| 5 | 社区兼容性目录 | 依信任级别决定 | 有可追溯实机证据、Issue/PR 治理与撤销机制 |

后续可增加：固件发布者的兼容性声明、支持设备版本、已验证功能清单、已知风险、回退版本、用户实机反馈，以及一个只读的“社区验证状态”时间轴。无论功能多丰富，都不应把“作者声明”显示为“实板已验证”。

## 10. 结尾：什么叫“设计到可以”

对硬件烧录工具而言，“可以”不是界面出现了进度条，也不是 CI 变绿。它至少意味着：固件来源可追溯、写入范围不可由前端任意扩大、设备身份在写前可验证、用户无法无意跳过关键硬件操作、结果能区分写入、恢复和功能验证。

EasyInput Flasher 已把这些原则落成独立工程、Release 合同和可维护的操作路径。下一阶段不是继续堆界面功能，而是用真实板卡把每一层证据补齐，再把这条可信路径开放给更多人的 Fork 和社区固件。

[EasyInput Flasher](https://github.com/FreeCodeCampXYG/easyinput-flasher) 想做的不只是一个固件下载器，而是一个面向 EasyInput V2.0 的硬件应用 Hub：像 Skill Hub 帮人发现、理解和复用能力一样，让每个人都能发现、制作、验证和体验硬件应用。

我们欢迎大家一起参与，把自己的想法变成可以在真实硬件上玩的应用：按键与编码器交互、灯光效果、音频体验、BLE 工作流、Host Action、效率工具、游戏化玩法、教学项目，或是让更多系统能稳定识别 EasyInput 的兼容性改进。没有固件开发经验也可以从设备测试、文档、界面可用性、故障复现和社区教程开始。

### 11.2 共创的约定

硬件应用可以自由探索，但设备写入必须可追溯。每个准备让他人烧录的版本都应提供公开 GitHub Release、固定 commit、`firmware-manifest.json`、三段固定镜像、SHA-256 和清晰的已验证范围。没有这些信息的项目仍可被讨论、浏览和改进，但不会自动获得写入设备的权限。

请在 [Issues](https://github.com/FreeCodeCampXYG/easyinput-flasher/issues) 提出想法、兼容性结果或问题；准备好可复现改动后，通过 Pull Request 参与共建。贡献指南、固件发布规范和社区教程已经在仓库中，维护者审核、CI 与实机证据会共同保护每一块设备和每一位尝试新功能的用户。

目标不是建立一个由少数人维护的“固件下载站”，而是让硬件应用像软件 Skill 一样可发现、可解释、可验证、可回退，并由社区持续丰富。欢迎把你的第一个 EasyInput 应用带进来，一起把它做成真正大家都能玩、也敢放心玩的硬件应用 Hub。
